## What this is

A take-home project: an AI agent that interviews a person about a business process, finds the gaps they didn't mention, and produces an SOP (Standard Operating Procedure) that the user reviews, approves, and downloads as a PDF. The AI agent's behavior is what matters; the surrounding web app is deliberately minimal (one page, chat UI, no login, one hard-coded company and user, runs locally).

Implementation is by vertical slices (see `docs/implementation-plan.md`), all six done. Slices 1 to 5 are: the walking skeleton (chat, agent, readiness panel), the full interview (corrections, ordered procedure steps, an interview policy computed in code, a claims view, and an eval harness), review and approval (confirm and reject, an approval step, an SOP preview, and a locked session after approval), PDF export (`POST /sops/pdf`, the download button, and a leave-page warning), and document ingestion (a policy or handbook read with a proven citation, conflicts between sources, and the agent's `resolve_conflict` tool). Decision 65 later made an upload reference material rather than SOP content: `POST /documents/references` reads the document for the SOP the session describes and returns a few passages, which the interview puts to the person; see "Uploaded documents" below. Slice 6 is the handoff: `README.md` (run, test, evals, a demo walkthrough, what is and is not stored), a readiness check, and cleanup. Slice 7 is deployment, kept deliberately small: `render.yaml` for the API, the README's "Deploy" section for Vercel, and the OpenAI project spending limit as the only guard against strangers (no rate limit, no daily counter, no parser worker thread). The web address the API allows is `WEB_ORIGIN`, reduced to its origin; the API address the browser uses is `NEXT_PUBLIC_API_BASE_URL`, read at build time.

## Session model

One chat is one session, and one session produces one SOP; the same person interviews, reviews, and approves. The whole session is one JSON document (`SopSession`) held in the browser's `sessionStorage`. The server stores nothing: no database, no files, no in-memory sessions. Each API request carries the state it needs, the API validates it with a zod schema, and returns the updated state. Closing the tab clears everything; refreshing keeps it. There is no list of past SOPs.

States are only `draft` and `approved`. An approved SOP is read-only, not permanently immutable: `reopenSession` (`packages/sop-core/src/approval.ts`) puts it back to draft so it can be changed and approved again, clearing `approvedAt` and `downloadedAt` together and keeping no record that it was ever approved before — claims, messages, history, acknowledgements and the consistency review all carry over untouched. Starting a new chat is still how you write a *different* SOP; reopening is how you keep editing the same one. Review actions are confirm and reject only; they never edit a claim's content, so every content change goes through the agent and the single claim-writing path. From review the user goes back to chat to describe a change; the agent records it (resetting the claim to `observed`) and the review panel updates. A `conflict` is resolved by the user's final answer in chat.

Review, acknowledgement, approval and reopening all run in the browser through `sop-core`; there is no approval route on the API. `applyClaim` and the acknowledgement function refuse every write on an approved session, and the PDF endpoint recomputes the export gate itself (`canExportApprovedSop`: approved, no blocking gap, every advisory gap acknowledged, no unreviewed suggestion), because a forged session can still claim to be approved (the API guarantees the shape of an approval, not that a person clicked). `downloadedAt` is the only field that may change after approval without reopening, only from `null` to a timestamp, and only through `markSopDownloaded`: it records that the browser started the PDF download, not anything about the SOP, and (like the session) it dies with the tab; the downloaded PDF is the only durable record of whatever was approved when it was made — reopening and re-approving does not keep a copy of the state it replaces, so downloading before reopening is the only way to keep one. The session document has a `schemaVersion` (now 7); a session stored by an older version is discarded with a notice, never migrated. The session holds a few passages and their citations from a document and nothing else: never the parsed text, which would ride along in every chat and PDF request (the browser guards the session at `MAX_SESSION_TRANSPORT_BYTES` when a document is added, and passages count toward the same text cap as claims).

Keep it that way: never write message or document text to server logs, and set `store: false` on every model call. Details are in `docs/scope-v1.md` §3 and §8.

## Invariants the whole design rests on

These span several modules and are easy to break by accident. The product's promise is that the model can propose but never silently resolve what it doesn't know.

- **A claim is the unit of state.** Every fact about the SOP is a claim with a status (`confirmed | observed | proposed | unknown | conflict`), a source, and an authority tier. The SOP document is a rendering of claims, never the other way round. A passage from an uploaded document is not a claim: it is reference material the interview puts to the person.
- **Only a human action produces `confirmed`.** The agent's tool set must contain no way to confirm; the tools are typed to `AgentClaimCommand`, so a model cannot build a review command. The agent may `correct` a confirmed claim (it drops to `observed`) but cannot withdraw or blank one. A passage from a document enters the SOP only as the person's own statement, after the agent put it to them and they agreed, or when they stated the same rule in their own words before being asked (an `observed` claim that rests on the passage, never `confirmed`, and never with more authority for being in a document), and a `conflict` (a passage that disagrees with what the person said, or two documents that disagree) is resolved only by the user's own final answer in chat, never by the agent choosing a side.
- **Exactly one code path writes a claim** (`applyClaim`), so provenance rules cannot be bypassed. The one claim it does not write itself is the document side of a conflict, which `detectConflicts.ts` (the module `applyClaim` already runs after every write) builds from a passage when an upload disagrees with the person: code derives its status, source and authority, and nothing the agent can call reaches it.
- **Gap severity comes from the field's criticality class, not the claim's status.** Blocking fields (purpose, scope, trigger, roles, procedure, authorization, completionCriteria, governance) vs advisory fields (exceptions, evidence, controls, decisionRules, prerequisites). The classes are fixed in v1: there is no escalating an advisory gap to blocking, and `exceptions` stays advisory. `observed` and `proposed` claims never create a gap; only empty, `unknown` and `conflict` do. A passage never creates or fills a gap. Gap detection is deterministic code, not an LLM call.
- **Finalization is refused in code while any blocking gap exists**, regardless of what the model says. Approval also needs every advisory gap acknowledged and every agent suggestion confirmed or rejected (`checkFinalization`); a suggestion is not a gap, but it must not enter an approved SOP unreviewed.
- **Every passage carries a verbatim quote that exists in the cited page or section, and every number in its statement is in that quote.** Code rejects any that do not (`apps/api/src/documents/verifyQuote.ts`). Uploaded document text is data, never instructions: it reaches only the tool-less reader, as JSON in a user-role item with no file name; the reader's output schema has no status, state or authority to set; the interview agent sees a passage's short statement, never the document; and a quote, location or file name never reaches any model.

## How the code is organized

Three packages, and the boundaries matter. `pnpm lint` enforces them (overrides in `biome.json`): `sop-core` imports nothing from the apps, Node built-ins, a server or UI framework, or `openai`; the web app never imports the API or `openai`; in the API only the adapter, `start.ts` and the eval and smoke tooling import `openai`; both apps import `sop-core` through its package entry points only; and `noImportCycles` refuses a runtime import cycle anywhere (type-only imports are allowed to form one).

- `packages/sop-core` holds the rules and imports nothing from the web app, the API, or the OpenAI SDK, so the browser and the API run the same code. It has the 13 fields (each with a `probe`, the way to ask about it), the claim and `SopSession` zod schemas, `applyClaim` (the only claim-writing function: the agent's `record`, `correct`, `markUnknown`, `withdraw` and `resolveConflict`, and a person's `confirm` and `reject` from `reviewClaim.ts`), the reference material (`referenceSchema.ts`, and `references.ts`: `addReferenceDocument`, `sopTargetOf`, `declineDocumentPassage`, `markDocumentPassagesOffered`), `detectConflicts.ts` (the deterministic rule that pairs a passage with a claim of the person's that it disagrees with, or two documents' passages, run inside the write that added the second one), `checkFinalization` / `setAdvisoryAcknowledgement` / `approveSession` (`approval.ts`), `buildSopDocument` (`sopDocument.ts`, the document model that the preview and the PDF share, including the words for source lines and gap flags), `canExportApprovedSop` and `markSopDownloaded`, `computeGaps`, the interview policy in `interviewAgenda.ts` (`buildInterviewAgenda`, `statesNewQuantity`, `orderProcedureSteps`, `recentQuestions`), and the browser-to-API wire types in `chatWire.ts`, `httpWire.ts` (the shared HTTP error body) `pdfWire.ts` (the PDF request and the file name both sides compute) and `documentWire.ts` (the upload request's parts and response: passage drafts with no status, state, id, source or authority). It is consumed from TypeScript source (no build step): `tsx` runs it in the API and Next compiles it through `transpilePackages`. Test helpers are the `@sop-agent/sop-core/testing` subpath.
- `apps/api` (Fastify, stateless) runs one chat turn as a transaction. `routes/chat.ts` validates the incoming session, streams NDJSON, and ends with exactly one terminal event: `commit` (the updated session) or `error`. `agent/runTurn.ts` is the tool loop over a working copy of the session; the whole turn, not one request, is what `runWithModelFallback` retries, so a failed attempt leaves no trace. `model/openaiModelClient.ts` is the only place that sends requests and reads responses through the `openai` SDK; everything else uses the `ModelClient` interface in `model/modelClient.ts`, which is what the tests fake. `routes/sopPdf.ts` renders the approved SOP with `pdf/renderSopPdf.ts` (pdfkit, standard Helvetica, in memory, given a `SopDocument` and never a session); every string goes through `pdf/toPrintableText.ts` first, because pdfkit silently prints the wrong glyph for a character outside WinAnsi, so each one becomes a visible `<U+XXXX>` marker and is counted. `routes/documentReferences.ts` takes the file and the session (validated like any other, refused if approved or if it states no purpose or scope yet), reads it with `documents/` (`parseDocument` from bytes with size, page, section, text and unzip bounds and named failure categories; `readReferencePassages`, the structured-output call behind `runWithModelFallback`, told the SOP's purpose, scope and what it already says; `verifyQuote`, which also checks every number; then code drops what the SOP already says, puts a passage that disagrees with the person first, keeps the reader's own most-needed-first order for the rest, and keeps at most twelve) and returns passage *drafts*: the route writes nothing, returns no session, and nothing is written to disk. The adapter also translates the SDK's errors into the provider-neutral ones in `model/modelErrors.ts` (refusal, unusable output, aborted, and a provider error that is `authentication`, `permission` or `unavailable`), so the fallback, the logs and both routes classify a failure without the SDK; the provider's own error rides along only as the `cause`, which the live smoke test prints and no log does. Only `start.ts` (the composition root), the adapter, and the live eval and smoke tooling import `openai`.
- `apps/web` (Next.js) owns the canonical session in `sessionStorage` (`lib/sessionStore.ts`) and replaces it only when a turn commits (`lib/chatTurn.ts`, `lib/useSopSession.ts`); `lib/extractDocument.ts` sends a file with the session and `useSopSession.uploadDocument` keeps the returned passages with `addReferenceDocument` on the latest session (all or nothing), refusing before the person has stated a purpose or scope; the upload panel lists every passage, read-only, from `lib/referenceView.ts`; `lib/downloadSopPdf.ts` fetches the PDF and `lib/saveBlobAsFile.ts` starts the download under the name from `sopPdfFileName` (the API is cross-origin, so its `content-disposition` is not readable). `useSopSession` also applies review clicks, acknowledgements and approval locally (refused while a chat turn is in flight, built on the latest session from a ref). The review panel is built from `buildClaimsView` and the approval step from `buildApprovalView` (`lib/`, pure view models); each field expands to its claims (a claim that rests on a passage, and the document side of a conflict, show the quote and location; two claims in conflict show once, side by side, read-only), their earlier versions, and removed claims, and the SOP preview renders only `buildSopDocument`.

The model has six tools. Five are thin wrappers over one `applyClaim` command: `record_claim` (offers `observed` and `proposed` only), `correct_claim` (the claim keeps its id; the result is always `observed`), `mark_claim_unknown`, `withdraw_claim` (at most 3 per turn), and `resolve_conflict` (at most 3 per turn; the user's own wording replaces both sides of a conflict, and `documentSideClaimId` names the document side when the user says it is right or that both mean the same, so the answer keeps resting on that passage). `record_claim` and `correct_claim` also take `documentPassage` (`{passageId, userAgrees}`) when the claim is the user's answer to a passage. The sixth, `decline_document_passage`, writes no claim: it marks a passage the user turned down. Source and authority are derived in code, never chosen by the model. Every correction, unknown and withdrawal writes a history entry with the whole previous claim and the user message that caused it, so a change is never silent. A procedure is one claim per step; the order lives in the session's `procedureOrder`, and a step is placed with `insertBeforeClaimId`.

The prompt is split for caching and safety: `INSTRUCTIONS` (`agent/prompt.ts`) is static and identical on every call, and the current SOP state travels as a separate `stateItem`, the last input item, rebuilt on every model step. The state item holds the interview agenda computed in code (which fields to ask next, which not to ask, whether the SOP is ready to review, whether the last message stated a number, the last questions asked, and the document passages to put to the person). Claim text never goes into `instructions`. Only the last 16 messages go to the model; the claims are the memory. Anything the OpenAI SDK returns must go through `stripClientOnlyFields` before it is sent back, or the API rejects it (`parsed_arguments`).

## Uploaded documents

A document is reference material for the interview, never SOP content by itself (decision 65). It is read for the SOP the session describes, so an upload is refused until the person has stated a purpose or scope (`sopTargetOf`). The browser sends the file and the session; the tool-less reader (`documents/readReferencePassages.ts`) is told the purpose, the scope and what the SOP already says, and returns passages this SOP needs, each a short sentence written for this SOP plus a verbatim quote. Code verifies the quote, refuses a statement with a number the quote does not hold, drops what the SOP already says, puts a passage that disagrees with the person first and otherwise keeps the reader's own most-needed-first order, and keeps at most twelve, as many as the reader is asked for. The order is not ranked by field on purpose: a manual test showed field ranking keeps rules the reader misfiled under a blocking field and drops the core facts. The browser keeps them in `session.references` (at most five documents and 36 passages a session) with `addReferenceDocument`, which also raises any conflict they bring. A passage fills no gap and is never printed.

The interview agenda then hands the agent at most two passages at a time, both about one field (`selectDocumentPassages`), and only their statements. They are withheld while a conflict, a `restatement_mismatch` or a `claimDepthQuestion` waits, and they come before a consistency question about an omission, which `runTurn.ts` then leaves unmarked for a later turn when the reply asked a passage (and marks as usual when it passed over every passage it was shown). A passage handed to the agent is marked offered when the turn commits only if the reply put it to the person (`settleShownDocumentPassages`: the reply names a document and enough of the passage's words and figures appear in it, `usesPassageWording`; overlap alone counts "Who approves refunds?" as asking "The manager approves refunds"); one the reply passed over stays open, goes behind the passages not handed over yet, and after `MAX_TIMES_NOT_ASKED` (3) turns is no longer handed over, staying "not discussed" in the upload panel. Marking every handed-over passage offered lost one for good in a manual test, when the agent asked a general question instead. `pendingDocumentPassages` keeps the latest offered ones visible so the answer can be linked. The answer goes through the ordinary tools: `record_claim` or `correct_claim` with `documentPassage.userAgrees` true writes the person's own `observed` statement resting on the passage (`basedOnPassageId`; `applyClaim` refuses a passage never offered, and a number neither the passage nor the user's message holds); an agreement may also rest on a passage in `documentPassages` not yet put to the person when their message already states that rule (code requires their message to use the passage's wording, every figure to come from their message, and both their message and the statement to state exactly the passage's figures and frequencies, keep its limit words and match its negation (`keepsPassageMeaning`, which counts "no", "never" and "can't" as "not"); word overlap alone cannot tell "may extend" from "may not extend"), since recording it alone would raise a conflict between two things that say the same; `userAgrees` false records their own answer and declines the passage, so it is not raised as a conflict; `decline_document_passage` turns one down with nothing recorded; unlike an agreement, it also takes a passage handed to the agent this turn, so a passage that is not a rule of the process at all (a document telling the reader what to do) can be dropped the moment the agent sees it, without being repeated to the person. A later correction without a passage answer drops the link (it stays in the history), the same trade-off as correcting any other claim. A passage is judged against the purpose and scope claims that existed when it was read: once any of them is withdrawn or replaced, it is stale and never offered again, and the person uploads the document again to read it for the new target. A passage that disagrees with what the person states (their own words, or a suggestion they confirmed), now or later, becomes the document side of a `conflict` pair, and `resolve_conflict` settles it; an answer that rests on the document side (`documentSideClaimId`, refused unless it keeps that side's figures, limits and negation) leaves that passage `used`, not `settled`. A claim resting on a passage put to the person takes the passage's effective date; any other claim (their different answer, a rule they stated before being asked, a conflict answer that does not rest on the document) takes a document's date only when their message states that whole date as one expression (`withoutCopiedDocumentDate`, `statesCalendarDate`), since the same value alone does not show it was copied. A different approver or actor is not caught by these checks and stays the agent's reading, as with any agreement. The SOP prints no note beside a claim that rests on a passage, since the citation already says where it came from; the review panel still shows it. Everywhere else a note prints as its own sentence after the source label.

An agreement must be in the passage's own field (`passage_field_mismatch` otherwise), so a document's citation cannot land on an unrelated claim. It also rests on the agent's reading of the user's reply, the same trust every `observed` claim rests on, with the number check narrowing it; unlike the old `extracted` rule, a passage the user agreed with needs no review click before approval, which is deliberate: the user's answer in chat is the review. Known, accepted limits: relevance is judged once, at upload, so a passage the reader left out is not recovered when the scope changes without a new upload; and code checks a statement's numbers against its quote, not its meaning, so a wrong paraphrase is caught only by the person, who sees the quote beside it in the upload panel and answers it in chat.

## The consistency review

Field gaps say what is empty; they cannot say that the Finance Director appears under roles and authorization while no procedure step reaches that tier, that nothing says what happens to a refused request, or that a $500 approval threshold is stated as "more than $500" in one field and "$500 or more" in another. When no blocking gap remains, no conflict is unsettled, and the person has not said they are out of time, `runTurn.ts` makes one structured model call (`agent/consistencyReview.ts`, only when the stated claims changed — including again within the same turn if that turn's own writes change them after it ran, since a stale review offers nothing) that returns up to four findings across five categories — four kinds of omission (`unreached_role_or_tier`, `missing_outcome_path`, `deadline_without_consequence`, `imprecise_threshold_or_term`) and one kind of disagreement (`restatement_mismatch`: the same rule stated with a genuinely different value or boundary, in the same field or across different ones — not restricted to different fields, because `detectConflicts.ts` never compares two things the person said, even within one field, and the review never sees a claim already flagged `conflict` either). `sop-core/consistencyReview.ts` validates the output (ids must exist, the count and length limits hold, a `restatement_mismatch` needs at least two distinct claims and a `targetField` among their own fields, an earlier finding must be carried or resolved) and stores it as `session.consistencyReview`; the interview agenda then hands the agent one `consistencyQuestion` at a time (each once, at most four a session), naming each related claim's field and current wording so the agent can explain a disagreement without guessing which field is which. It is deliberately not a gap: it is a question with no effect on `readyToReview`, `checkFinalization` or the PDF, it is not a claim (no tool, no status, `applyClaim` is untouched, and the model never picks a side), and a failed or refused review is skipped (fail-open) and not retried until the claims change. The review reads only `observed` and `confirmed` claims, never the conversation, a suggestion or a passage; a passage the person agreed with is their own statement and is read like any other claim, which is the only thing that can catch a document contradicting itself, since `detectConflicts.ts` never compares two passages from the same document. Once the person answers a `restatement_mismatch`, the agent corrects every affected claim in place with `correct_claim`, never adding a new claim next to them. Because `wasOffered` flips at the end of the turn the question was asked, `consistencyQuestion` alone would vanish from the state on the very next turn — normally exactly when the person answers — so `pendingMismatchClaims` keeps an offered-but-unresolved mismatch's claims (id, field, statement) available until a later review reports them resolved, the same way a same-field `conflict` stays visibly unsettled until it actually is. A known, accepted limit: a model step that both streams a consistency question and calls tools can make one reply ask two, since only the last step's question is marked offered. Its output schema states no lengths or counts, because provider structured output does not reliably support them; code enforces them.

## The claim-depth review

The consistency review only ever compares claims to each other or to a fixed vagueness test; it cannot say that a single procedure step, on its own, leaves a reader unable to carry it out — "the operator submits a maintenance request" says nothing about what the request must contain. `runTurn.ts` runs a second, separate structured model call for this (`agent/claimDepthReview.ts`), scoped to `procedure` steps only in this release: whenever a stated (`observed`/`confirmed`) procedure claim not yet asked about changes, it judges just that step's own operational completeness against four fixed focuses (`required_input`, `condition_or_criterion`, `destination_or_handoff`, `observable_result`), reading the rest of the SOP only as read-only context to avoid re-asking for something already recorded elsewhere. `sop-core/claimDepthReview.ts` validates the output (a finding must target a real candidate, at most one per claim, an earlier finding must be carried under the same target or resolved) and stores it as `session.claimDepthReview`; the interview agenda then hands the agent one `claimDepthQuestion` at a time (each claim asked about at most once, ever, and at most four questions a session), naming the step's position so the agent can point at it without guessing. It outranks `askNext` and a consistency question about an omission — it is about the thing the person just said — but not a `restatement_mismatch`: then the SOP already gives a reader two different answers, so `selectReviewQuestions` (`interviewAgenda.ts`) withholds the claim-depth question, unoffered, for a later turn, and `runTurn.ts` runs the consistency review even on a turn where a claim-depth question is waiting, since only that review can find the mismatch. The agenda and the turn's offered-question bookkeeping both go through `selectReviewQuestions`, so the question the model sees and the one marked offered never disagree. Like the consistency review, it is deliberately not a gap (no effect on `readyToReview`, `checkFinalization` or the PDF), it is not a claim (no tool, no status, `applyClaim` is untouched, and the model never invents the missing detail), and a failed review is skipped (fail-open) and not retried until the candidates change. Its persisted shape differs from the consistency review's in one way worth noting: a finding is removed from `findings` the instant it is offered (moved into a permanent `askedClaimIds` list instead), so there is never more than one "most recently offered" question to disambiguate the way `restatement_mismatch`'s `offeredSequence` has to — `pendingClaimDepthTarget` only ever needs to remember `lastOfferedClaimId`, and it carries no claim text at all (just an id, a field and a position), because the state item's own `fields` list already repeats every claim's wording every turn regardless. It does still need to notice when that pointer has gone stale, since the person's answer arrives through the ordinary `correct_claim` tool, which knows nothing of this bookkeeping: `lastOfferedClaimTextHash` is a snapshot of the target's text taken the moment it is offered, and `pendingClaimDepthTarget` returns null once the live text no longer matches it (the answer landed), the claim was withdrawn, or the claim is now half of a `conflict` (never `correct_claim`, only `resolve_conflict`). This hash check cannot tell "the person answered" apart from "the person corrected the same step for an unrelated reason" — both change the claim's text, so both clear the pointer, and since `askedClaimIds` also guarantees that claim is never asked about again, an unrelated correction landing before the real answer permanently and silently drops the original follow-up. A correct fix needs the claim's original text at offer time, not just its hash, to tell a genuine extension of the old wording apart from a mere difference — which reintroduces the duplicated-claim-text cost this design was built to avoid, and still could not catch an answer that happens to reword the original portion too. Deferred, on the same precedent as the paragraph above: the step itself stays fully visible and editable in the ordinary review UI regardless, so nothing is hidden from the person — only the agent's own proactive nudge is lost, bounded by the same four-questions-a-session cap. `claimDepthReview` was added to the session schema as a nullable field defaulting to `null`, with no `SESSION_SCHEMA_VERSION` bump, the same way the consistency review's own `offeredSequence` was added. A known, accepted limit, the depth-review counterpart to the consistency review's own "one step, two questions" limit above: the prompt allows the agent to ask a `claimDepthQuestion` and a tightly related `consistencyQuestion` together in one reply, but `runTurn.ts` only ever marks the depth question offered when both are present that turn (see below) — so if the agent does combine them, the consistency question is not marked offered and can be shown again on a later turn. This is deliberate: the alternative (marking both offered whenever both are merely shown, whether or not the reply actually asked both) risks the opposite, worse failure — silently burning a question's one-time budget when the model prioritized the depth question instead and never asked it at all, exactly the bug an earlier round of review found and fixed. Between an occasional repeat and a silently lost question, the repeat is the one this design accepts.

## LLM configuration

The LLM is OpenAI: primary `gpt-5.6-sol`, fallback `gpt-5.6-luna`. Configuration lives in a git-ignored `.env` at the repo root (copy `.env.example`): `OPENAI_API_KEY`, and optionally `LLM_MODEL` / `LLM_FALLBACK_MODEL` to override the two model names. The API scripts load it with Node's `--env-file-if-exists`. The web app reads its own `apps/web/.env.local` (only `NEXT_PUBLIC_API_BASE_URL`, default `http://localhost:4000`); the OpenAI key never goes in `apps/web`.

Every model call goes through `runWithModelFallback` (`apps/api/src/model/modelFallback.ts`): it retries on the fallback model when the primary refuses, returns unusable structured output, is aborted (an attempt's own time limit), or fails with a provider error, but never on authentication or permission errors (`isWorthTryingAnotherModel` in `model/modelErrors.ts`). There is no server-side fallback, so keep new model calls behind this wrapper. The agent (`zodResponsesFunction`) and document reading (`zodTextFormat`, `ModelClient.runStructuredOutput`) both use the Responses API. Function calling and `reasoning.encrypted_content` were confirmed live on both models.

## Things that are easy to trip over

- Component tests in `apps/web` opt into a DOM with `// @vitest-environment happy-dom` at the top of the file (pure view-model tests stay in node). The `happy-dom` storage does not route through `Storage.prototype`, so a test that counts or fails writes installs its own storage. To add a dependency on this volume, pass `--store-dir "$PWD/.pnpm-store"` to pnpm, or it refuses with `ERR_PNPM_UNEXPECTED_STORE`.
- `pnpm eval` is not part of `pnpm test` on purpose: `apps/api/vitest.eval.config.ts` only includes `src/evals/**/*.eval.ts`. The scripted-expert scenarios are in `src/evals/scenarios.ts`; assertions are pure functions over a transcript (`assertions.ts`) and are unit-tested offline. `safety` assertions must pass on every trial, `behavior` ones on 2 of 3. Run files land in `apps/api/evals/runs/` (git-ignored).

- The repo is on an external volume, so pnpm creates its package store inside the project at `.pnpm-store/`. It is git-ignored and excluded from Biome; do not commit or lint it.
- `fixtures/documents/` holds generated samples (PDF, DOCX, Markdown) that tests read; the parser tests also build harder cases in memory (`apps/api/src/testing/documentFixtures.ts`). Regenerate with `pnpm fixtures:documents` rather than editing them by hand, and expect a tiny binary diff. `vendor-payment-policy.md` and `vendor-payment-memo.md` are a deliberately contradictory pair (the memo replaces the $10,000 threshold with $25,000): uploaded together for a vendor payment SOP they produce a conflict. `northstar-store-policy.pdf` is a store-wide policy far broader than any one SOP, modelled on a manual test; `relevance-key.json` scores it against two SOPs (cashier closing and store opening). `expected-fields.json` is the answer key that `pnpm measure:extraction` scores field labels against.
- Conflict detection is a heuristic on purpose (`detectConflicts.ts`): a passage and a claim of the person's (or two passages from different documents) in the same field, and either different numbers with a shared word, or, when neither states numbers or both state the same ones, at least half the shorter statement's words in common. A statement that only one side gives numbers for is one side being more specific, not a disagreement: the passage is offered as detail instead. A passage that says nothing the claim does not already say is not a conflict either. It over-flags a paraphrase rather than miss a disagreement, and resolving one costs a chat reply. Tune `CONFLICT_TOPIC_OVERLAP` before changing the rule. Statements with the same figures are compared on their other words too, so a restatement is flagged rather than a different approver missed. Known limit, accepted for v1: sources are compared by sanitized file name, so two uploads with the same name count as one source and a same-named revision cannot conflict with the earlier file (fixing it needs an upload id in the citation, schema v6).
- Claude Code's sandbox denies reading the repo-root `.env`, so a command run inside the sandbox cannot see the API key, and it does not allow listening on a port. The user runs live model commands from their own terminal. One API test (client disconnect aborts the model request) is skipped where listening is not allowed.
- Scanned (image-only) PDFs are unsupported by design: the parser reports "no extractable text" instead of attempting OCR.
